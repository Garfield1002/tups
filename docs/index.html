tups

Ultra-micro containers for coding agents. Give an agent its own filesystem, network, and process namespaces — then move the live session to another machine between turns.

# one-shot, in a private namespace
tup run web -- cargo test
# long-lived, supervised, PID 1
tup up  web
# ship the whole session elsewhere, resume it there
tup move web user@host

What it does

▣

Contains the blast radius

A mistake stays inside the project — its files, its ports, its process tree — instead of reaching the rest of your machine.

⇄

Relocates a session

Pause an agent on one box, ship it to another, resume it there — with the same internal addresses on every server.

⚿

Lends capabilities

The container can git push without holding a key — the host performs the filtered operation on its behalf.

Why this way

Most isolation tools build an image and run it under a daemon as root. That buys strong multi-tenant security, and it costs a build step, a copy of your files, a background service, and seconds of startup.

A coding agent doesn't need any of that. It needs its own blast radius and a fast loop. So a tup container is just namespaces laid over your real working tree — no image, no daemon, no sudo. Binaries live once in a shared read-only /nix/store, so a container starts in ~10 ms and the agent edits your files directly. Nothing to sync, nothing to rebuild.

Using credentials without holding them

A container often needs to use a secret — git push over ssh — but should never be able to read it. Both grants are deny-by-default: with nothing declared, the container reaches no host credentials at all.

Gates preferred

The container holds only a socket. The host is the reference monitor — it reads the policy, filters the request, and runs the operation itself. tup push main inside the box becomes a host-side git push to the one remote the policy names. It can do only the declared operation; no key or token ever enters the container.

Agents

Forward a socket to a host ssh-agent, not the key. git inside the container signs GitHub's challenge over the socket; the private key never crosses the boundary, and the agent dies with the session. Use this when the container must run git itself.

Dogfooded: this repository was first published through its own gate — a credential-less tup push inside the container drove a host gatekeeper that did the authenticated push.

Get started

Linux with unprivileged user namespaces. Build with Cargo:

# binary at target/release/tup — put it on your PATH
cargo build --release

Two backends render one spec, so they can't drift: pyrex (default, raw namespace syscalls, no helper — falls back to bwrap where user namespaces are unavailable) and bubblewrap (TUP_SANDBOX=bwrap). tup assumes a cooperative agent: the isolation catches mistakes, and egress stays open for the model API and package mirrors.
